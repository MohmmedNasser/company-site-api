# PHP 8 attribute-based `#[Fillable]` / `#[Hidden]`

## What is it?

`app/Models/User.php:13-14`:

```php
#[Fillable(['name', 'email', 'password'])]
#[Hidden(['password', 'remember_token'])]
class User extends Authenticatable implements MustVerifyEmail
```

`#[Fillable]` and `#[Hidden]` are native PHP attributes (the `#[...]`
syntax, not docblock annotations) that Laravel 13's Eloquent reads via
reflection at model-boot time. They do exactly what the older
`protected $fillable = [...]` and `protected $hidden = [...]` class
properties did — `$fillable` whitelists which columns `User::create($data)`
and `fill()` are allowed to mass-assign; `$hidden` strips those keys when
the model is serialized to JSON (which matters here because
`ProfileController::edit()` and every `Inertia::render()` call that includes
`$request->user()` serializes the model straight into the page props sent
to the browser).

## Why is it here, in this project specifically?

This is what `laravel new --react` generated by default when scaffolding
against Laravel 13 (confirmed against the framework version pin at
`composer.json:12`, `"laravel/framework": "^13.17"`) — it isn't a choice
this project made deliberately, it's simply what a fresh Laravel 13 app
looks like now. It matters here specifically because `password` appears in
**both** attributes: `#[Fillable]` lets `CreateNewUser`
(`app/Actions/Fortify/CreateNewUser.php`) and `ResetUserPassword`
(`app/Actions/Fortify/ResetUserPassword.php`) write a hashed password onto
the model, while `#[Hidden]` guarantees that same password hash never
leaks into an Inertia page's JSON payload — the two attributes are doing
opposite jobs on the same field, and Fortify's auth flow depends on both.

## What was the alternative, and why was it rejected?

The alternative is the pre-Laravel-13 property style:

```php
protected $fillable = ['name', 'email', 'password'];
protected $hidden = ['password', 'remember_token'];
```

Nothing was rejected here — no code in this project ever used the property
style, since `laravel new` generated the attribute style from the start.
The two forms are functionally identical (Eloquent's `HasAttributes` trait
checks the attribute first and falls back to the property if no attribute
is present), so this is purely a "what does new Laravel code look like"
note, not an architectural decision.

## What breaks if it is removed?

Deleting `#[Fillable(['name', 'email', 'password'])]` from
`User.php:13` without replacing it means `User::create()` (called nowhere
directly, but via Fortify's `CreateNewUser` action) and `$user->fill()`
(called in `ProfileController::update()`) silently ignore every field —
Eloquent's default with no `$fillable`/`#[Fillable]` present at all is
mass-assignment being denied entirely, so registration and profile updates
would throw `MassAssignmentException` in `APP_DEBUG=true` or silently no-op
in production. Deleting `#[Hidden(['password', ...])]` at line 14 means
`$request->user()` — shared into every Inertia page via `HandleInertiaRequests`
(`01-inertia-shared-props.md`) — would serialize the bcrypt password hash
straight into the HTML `<script>` payload of every authenticated page.
